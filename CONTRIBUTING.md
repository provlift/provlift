# Contributing to provlift

Thanks for your interest in improving `provlift`. Bug reports, documentation
fixes, feature ideas and code are all welcome.

By participating you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).
Please report security vulnerabilities privately as described in
[SECURITY.md](SECURITY.md), not in a public issue.

## Before you start

- **Bugs:** open an issue using the *Bug report* template. Include the
  `provlift version` output, whether you use Terraform or OpenTofu, the command
  you ran and a minimal configuration that reproduces the problem.
- **Features:** open an issue using the *Feature request* template before
  writing a large change, so the approach can be agreed first. Small fixes can
  go straight to a pull request.
- Check the [known limitations](docs/troubleshooting/README.md#14-known-limitations)
  and the [architecture guide](docs/architecture/README.md#7-known-limitations);
  some behaviour is deliberate.

## Development setup

Requirements:

- Go 1.26 or newer (the exact toolchain is pinned in `go.mod`)
- Git
- Terraform or OpenTofu, only if you want to exercise `upgrade` or `validate`
  end to end. The unit tests use a fake registry and a fake Terraform binary and
  need neither network access nor Terraform.

```sh
git clone https://github.com/<your-username>/provlift.git
cd provlift
go build ./...
go test ./...
```

Run the CLI from source against any Terraform repository:

```sh
go run ./cmd/provlift list -C path/to/terraform-repo
go run ./cmd/provlift upgrade -C path/to/terraform-repo --level patch --dry-run
```

## Before opening a pull request

Run the same checks CI runs:

```sh
gofmt -l .            # must print nothing; fix with gofmt -w .
go vet ./...
go mod tidy           # must leave go.mod and go.sum unchanged
go test -race ./...   # -race needs cgo; plain go test ./... is fine locally
```

CI additionally enforces at least 80% test coverage, cross-compiles for Linux,
macOS and Windows, lints the GitHub Actions workflows with `actionlint`, and runs
an end-to-end upgrade against the real Terraform registry. See
[docs/development](docs/development/README.md) for details of the test strategy.

Guidelines:

- **Add tests.** Every behaviour change needs a test; bug fixes should include
  a regression test that fails without the fix.
- **Respect the design invariants** in
  [docs/architecture](docs/architecture/README.md#2-design-invariants) — for
  example, `provlift` never writes `.terraform.lock.hcl` itself, and it only
  rewrites a constraint that would otherwise block the target version.
- **Keep it provider-neutral.** `provlift` has no per-provider code; anything
  that works for one provider must work for all of them, in any registry.
- **Update the docs** under `docs/` when you change flags, output or behaviour.
  The workflow templates in `examples/workflows` are tested by
  `go test ./examples/workflows`.

### Docs site

The command overview at https://provlift.github.io/provlift/ is an Astro site
in `docs-site/`:

```sh
cd docs-site
npm ci
npm run dev     # local preview
npm run check   # type check
npm run build
```

## Commit messages

Releases and the changelog are generated by
[Release Please](https://github.com/googleapis/release-please) from commit
messages, so commits on `main` must follow
[Conventional Commits](https://www.conventionalcommits.org/):

```text
<type>(<optional scope>): <summary>
```

| Type | Use for | Release effect |
|---|---|---|
| `feat` | A new user-visible capability | minor version |
| `fix` | A bug fix | patch version |
| `docs` | Documentation only | none |
| `test`, `refactor`, `perf`, `chore`, `ci`, `build` | Everything else | none |

Mark breaking changes with `!` after the type (`feat(upgrade)!: ...`) or a
`BREAKING CHANGE:` footer, and describe the migration. Scopes usually name the
affected area, such as `upgrade`, `check`, `drift`, `registry` or `workflows`.

## Pull request process

1. Fork the repository and create a branch from `main`.
2. Make your change with tests and documentation.
3. Run the checks above.
4. Open a pull request and fill in the template. Use a Conventional Commit
   style title — pull requests are squash-merged, so the title becomes the
   commit message on `main`.
5. A maintainer will review it. CI must be green before merge; please respond
   to review comments by pushing new commits rather than force-pushing, so the
   review history stays readable.
